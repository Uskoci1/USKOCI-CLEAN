## 1. Findings that matter most

1. **10.0 GB of live Actions artifacts** (1,066 artifacts, none expired; retention setting = 90 days max). 5.66 GB are `USKOCI-DEV-APK` (161 artifacts, ~11 per day, 14-day retention) from `build-android-dev-apk.yml`; 1.72 GB are `uskoci-source` from `pre-p4-integrity.yml` (a `git archive HEAD` zip of the **whole tree - 242 MB raw, 207 MB of it `docs/`** - on every run); **118 artifacts / 1.5 GB are orphans** (no workflow at the pin can produce those names: `pre-v3-staged-sql` 67 x 22 MB, expiring 2026-12-11/12). 36 workflows upload artifacts without `retention-days` (default 90 days).
2. **The repository is PUBLIC** and Actions default workflow permissions are **`write`** (`default_workflow_permissions: write`, `can_approve_pull_request_reviews: false`). 23 workflows request `contents: write` (4 at workflow level: `build-android-dev-apk`, `control-tracker-refresh`, `round40-control-refresh`; `r18-storage-apk-20260926` requests `actions: write`; the rest at job level), 22 contain `git push` (mostly the P6/R18 evidence-commit steps that push to the canonical branch) and 1 recreates the `dev-latest` release. Consider setting the repo default to `read` (owner setting, not touched here). Static check for that change: all 23 workflows that `git push` or manage releases already declare `contents: write` themselves and all 125 files carry a `permissions:` block, so none relies on the default write token (the one `gh api` POST caller, `r18-storage-apk-20260926.yml`, declares `actions: write`); prove it with one dispatch of `control-tracker-refresh` after the switch.
3. **55 of 125 workflows have a `push.branches` filter that names only frozen/merged branches** (30 list only `work/pre-v3-engine-integration-20260911`; RU/N/D03 proofs list their own merged branch). They can never fire automatically on canonical; recent runs on canonical (pkg003..pkg050, 5-9 days ago) were `workflow_dispatch`. Deleting those branches (BRANCHES.md) changes nothing operational for them: they stay dispatch-only. 99 workflows already declare `workflow_dispatch`.
4. **81 workflows re-run themselves when their own file changes** (`push.paths` contains the workflow path) and several fire on sentinel text files (`p6_client_final_check.txt`, `p6_native_apk_build.txt`, `p6_native_apk_run.txt`): "touch the file to re-run" is the working pattern. Every one of the 50 canonical-push workflows has a path filter (no every-push workflow).
5. **Near-duplicate YAML**: 12 similarity clusters (Jaccard >= 0.6 over normalised lines) cover 58 workflows; largest: `pkg038..pkg051` (10), `p6-round59..67` (9), `pkg027/029/031..037` (8), `notifications/d03` proofs (7). Consolidation into parameterised reusable workflows is a C1 job, not C0.
6. **AGENTS.md is edited by CI**: 19 workflows `git add AGENTS.md docs/control/... ROUND_nn_*.md` and push to canonical (the bot made 71 of the 2,141 commits reachable from the pin; `docs/control/stanje.json` changed in 175 commits, `docs/control/out/tabla.html` (316 KB) in 74). This is why AGENTS.md is 125 KB; see DOCS.md before replacing it, otherwise the P6 record steps will keep re-growing it.
7. **GitHub Releases hold 10 public DEV APK pre-releases** (~0.65 GB, see BRANCHES.md section 7) and the Actions cache holds 2.07 GB in 11 caches.
8. **Hygiene**: 5 of 10 external actions are pinned to floating tags (`actions/checkout@v4` in 42 workflows, `setup-node@v4` in 50, `upload-artifact@v4` in 39, `setup-java@v5` 9, `setup-python@v5` 2); the rest are pinned to full SHAs (PR #48 "action pins" was only partially applied). Only one secret name is referenced anywhere: `DEV_ACCEPTANCE_PASSWORD` (workflow never run). No workflow references a Supabase access token, DB password or service key, so CI has no credential to mutate live DEV; the DEV project URL and the publishable client key are embedded as public build config in 11 workflows (by design, but the repository is public). A value-free scan of the pinned tree for credential shapes found no private key, GitHub/AWS/Slack token or live Supabase key in any workflow; the two JWT-shaped strings in `p6-native-apk.yml` and `p6-native-journey.yml` decode to the standard public local-stack demo key (`iss=supabase-demo`, `role=anon`), not a project credential.

### Legend

- **Trigger**: `push[canon|default|old-pre-v3|frozen xN]` = branch filter; `self` = own file in `paths`; `pathsN` = N path filters; `PR` = pull_request; `D` = workflow_dispatch; `C` = workflow_call (reusable).
- **Last run**: date of the most recent run (age in days), result (`ok`/`FAIL`), branch; **Runs** = total runs GitHub holds for that workflow; **Open pkg** = the open package it proves (P6/P0, P5, P7, P4/push, chat/voice, PKG045b, PKG051) or `infra`.
- **Refs**: `called xN` = other workflows `uses:` it; `docsH` = number of historical docs naming it; `scripts` / `supa` = scripts / supabase files naming it (zero active-doc mentions exist for any workflow file - active docs cite run ids and rounds, not file names).

## 14. Limits

- Trigger parsing is line-based; the 125 files were parsed without error but exotic YAML (anchors, multi-document) would be missed. Similarity is textual, not semantic.
- "Zero references" never proves a workflow is dead: proofs are started by hand (`gh workflow run`/dispatch) and cited by run id in docs, so file-name grep is weak evidence. Recency (last run) and open-package ownership carry the decisions.
- Run data is a snapshot taken on the morning of 2026-09-30; the P6 owner is running workflows continuously, so counts and "last run" values move every few minutes.
