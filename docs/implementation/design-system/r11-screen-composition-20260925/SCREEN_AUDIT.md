## Composition conclusions

The app already has useful structure: its bottom bar is limited to **Početna, Zadaci and Dogovori**; inner screens use Back or a close control; task and offer flows retain explicit reviews; settings have purpose-named sections. The next pass should remove repeated navigation and commands that compete with the current decision, while preserving every necessary state and recovery path.

A white, spacious screen does not require adding a large title, logo or search field. A control earns a place by advancing this screen's task, opening necessary detail, recovering a real interrupted attempt or returning to the relevant context. Empty/error states can have their own next action; that is not a reason to show the same recovery button during normal reading.

## Proposed fix order

These are composition priorities, not a statement that every item is an observed native defect.

1. **Conversation reading space at keyboard + very large text.** Finish the human Agreement chat work first, then inspect group and support composers separately. Their own headers, participant controls, paging and recovery blocks differ. Keep send/attachment reachable, accepted terms accessible and terminal state truthful.
2. **Discovery's hierarchy.** Search owns the top area; map/results own the body. Reduce repeated brand/header/tool weight, keep one understandable condition summary, retain full attribution, and preserve the list/pin context.
3. **People and decisions.** Candidate list → offer → public identity must lead with person, offered total, people, term and actual message. Comparison stays optional; exact selection confirmation and receipt recovery stay intact. Home and My applications should lead with their one next action.
4. **Safety target and block confirmation.** The current full Safety screen names “korisnik” without a visible trusted person/context. Its block/unblock button calls `editor.save(...setBlock)` directly at `SafetyScreen.tsx:35–43`; `useSafetyEntry.ts` only resolves and navigates. The blueprint explicitly requires confirmation for blocking. Add trusted identity/context and explicit consequence confirmation before changing the block. The blocked-list screen's existing unblock confirmation is a different path and does not close this gap.
5. **Long forms and support.** Worker profile, task place, review and new support request should disclose optional material and local edit commands by purpose. Keep one state-appropriate primary command. Do not remove readback/replay merely to make a screen shorter.
6. **Auth/recovery and the remaining static/settings family.** Remove duplicated intros, preserve ample input space, and verify keyboard/fixed footers. Keep About simple; do not make informational pages look like unfinished forms.
7. **Accept the coherent package on its actual build.** Capture representative screens and material error/recovery states; explicitly retain gaps. Then test actual navigation/commands in their separately authorized journeys. Passing source tests or showing a fixture does not accept provider, push, privacy, export, two-party or store flows.

Safety evidence: [src/ui/safety/SafetyScreen.tsx](<../../../../src/ui/safety/SafetyScreen.tsx>) lines 21–56 and 121–145; [src/ui/safety/useSafetyEntry.ts](<../../../../src/ui/safety/useSafetyEntry.ts>) lines 12–34; blueprint §7 “blokiraj osobu” confirmation. This is a client-flow finding, not a new server audit.

## Capture plan and honest coverage

[SCREEN_INVENTORY.json](SCREEN_INVENTORY.json) is the full machine-readable route inventory: route, display name, group, source/presentation paths, controls, search purpose, header/logo/nav, return path, source states, gaps, and exact existing gallery scene references.

[CAPTURE_PLAN.json](CAPTURE_PLAN.json) narrows it to **40 destination entries** plus **21 material surface/state entries**. Thirty-two active destinations have a relevant inert fixture; three further destinations can be captured through their existing authorized read-only route (`/zadaci`, `/potrebe`, `/profil/o-aplikaciji`). Five still require an already existing authorized context or additional inert fixture: `/auth`, `/oporavak`, `/potrebe/[id]/pregled`, `/prilike/[id]`, `/bezbednost`.

Only `dizajn-pocetna` and `dizajn-dogovori` read a `scene` query. Other galleries require selecting the exact visible label. Their keys must not be appended to a URI and then described as the requested state. The JSON records key, label, optional group and source line.

Root galleries are outside the real tab navigator. A Home or Dogovori fixture capture does not show the production bottom bar. Most picker galleries also reserve their own selection/back strip, changing available viewport height. Record that framing; do not silently equate it with the real route.

Both JSON files provide `accessibility_picker_label` as well as visible label/group. The privacy/publication galleries expose “group: label”; offer/candidate galleries expose “Galerija: label”. Match the freshly observed picker accessibility name. Only Home and Dogovori galleries support the recorded `scene` query; the other galleries require selecting an existing picker row.

A current-build receipt should name route/surface, actual versus fixture, scene, viewport/font scale, keyboard state, screenshot path and observed result. Keep “planned”, “captured” and “visually accepted” separate. At this audit handoff, all capture-plan entries are **planned, not observed**.

## Blueprint reconciliation and separate functional work

The current architecture deliberately differs from the historical blueprint in two places: map/list are one `Zadaci` root, and the bottom bar appears only on the three roots. Candidate detail, public identity and short edits can live in sheets while keeping the same decision/review semantics. Retired routes redirect and do not deserve duplicate redesigned screens.

The master checkpoint separately tracks server pagination/filtering, rating-comment support, AI provider/microphone/voice activation, push delivery, legal publication, privacy/export execution, real two-party journeys and release gates. None was re-audited or accepted here. Source-only UI composition must not add controls suggesting those capabilities are ready.
