## Proved current behavior

- One `mojiDogovori()` invocation calls `auth.getUser()` once, reads **P sequential pages (1–20, 100 rows/page), then C concurrent review RPCs**, where C is every returned `COMPLETED` row. Thus **P + C RPCs**, plus the auth call; 500 completed rows alone mean 505 RPCs. More than 20 pages rejects before enrichment. There is no enrichment cache, concurrency cap, deadline or cancellation. [Reader and enrichment](../../../../src/data/agreementClientService.ts:566), [auth](../../../../src/data/agreementClientService.ts:196).
- All C requests are awaited together. Errors/malformed eligibility become `ocenaMoguca: false`; a never-settling request prevents collection resolution. Home waits for its four reads together, with a 15-second timeout per section; Agreements has a 15-second collection timeout. These races do not cancel the underlying work. Calendar also uses this enriched reader. [Home](../../../../src/app/(app)/index.tsx:33), [section timeout](../../../../src/data/homeSnapshot.ts:44), [Agreements](../../../../src/app/(app)/dogovori.tsx:44), [calendar](../../../../src/app/(app)/raspored.tsx:19).
- The existing test proves three completed rows cause exactly three review reads, only `eligible: true` marks due, and an error maps false. It does not prove a concurrency bound or stalled-read availability. Separate review-service tests verify account/Agreement identity and authoritative receipts. [Collection test](../../../../src/data/__tests__/cdl-a01-agreement-read-equivalence.test.ts:94), [receipt tests](../../../../src/data/__tests__/reviews-authority.test.ts:35).

## Existing RPCs do not consolidate eligibility

The local list-function body contains no own-review/eligibility field; its `ACTIVE` scope includes only `CONFIRMED`/`AWAITING_REQUESTER`, excluding completed work still awaiting a rating. Later profile-ID enrichment adds identity fields only. The own-review RPC accepts **one UUID** and checks own review, completed Agreement/execution and account restriction. The Home attention aggregate has four reasons, none for ratings. No existing bulk eligibility RPC was found in local definitions. Account reputation counts cannot establish which Agreements I have rated. These are repository-contract findings, not a fresh deployed-schema attestation. ## Recommendation — smallest safe client slice

Replace `Promise.all` fan-out with an account/revision-owned pool (for example four in flight), cancellation and a collection-wide budget below the outer timeout; per-request timeouts alone multiply across batches. This bounds load, **not total call count**. Reuse the strict own-review receipt decoder rather than accepting an arbitrary `{eligible:true}`. [Existing decoder](../../../../src/data/reviewsClientService.ts:57).

To return usable accepted work when enrichment expires, add explicit rating-read **unknown/unavailable** state; do not expand today's false fallback into a claim of “rated”, zero due or an exact count. Home's total/single-rating shortcut and Agreement active/history classification currently depend on one boolean, so they need that small availability contract before partial enrichment can be honest. Keep detail/review revalidation. A pool alone is a safe mitigation, not full RC-03 closure. [Consumers](../../../../src/data/homeSnapshot.ts:116), [classification](../../../../src/ui/v2/AgreementCollectionPresentation.tsx:45).

Proposed checks only: 500 completed rows with measured peak concurrency; one stalled request; budget cancellation/late resolution; account switch; rated/due/unknown mixtures; no false Home total or silently lost next action. A true P-only solution needs a separately approved server list/bulk-eligibility contract.
