WHAT DETERMINES PRICE TODAY, STEP BY STEP
1. TASK. The requester declares it on needs: mode (MY_PRICE or OFFERS only), requester_price_rsd (NULL or >0), price_basis (NULL, TOTAL or PER_PERSON, and only with MY_PRICE), required_slots 1..50. The AI review writers enforce 'MY_PRICE needs an amount' and 'non-MY_PRICE price is NULL', with a validator cap of 1..100,000,000. The legacy rpc_confirm_need_edit (authenticated EXECUTE, no src caller, md5 450b6f8d) and direct owner writes while status is DRAFT have no such coherence rule. After the first Dogovor the task price is frozen (NEED_EDIT_LOCKED_AFTER_FIRST_DOGOVOR).
2. SUBMIT. The client sends p_price_rsd. For MY_PRICE the client derives and locks it from the same Need read (fixedApplicationPrice). For OFFERS the worker types it. The server helper rules are:
 - null or <=0 raises INVALID_PRICE 22023.
 - MY_PRICE with no task price raises FIXED_PRICE_NOT_READY P0001.
 - NULL basis requires price = task price whatever the application covers.
 - PER_PERSON requires price = task price::bigint x covered_slots.
 - TOTAL requires covered_slots = required_slots (else TOTAL_PRICE_REQUIRES_ALL_SLOTS) and price = task price.
 - Any other basis raises UNKNOWN_PRICE_BASIS.
 - OFFERS has no rule beyond >0.
 The price is stored VERBATIM (never rewritten) in marketplace_responses.price_rsd and marketplace_response_versions.price_rsd (int4, CHECK >0). p_price_rsd is part of the request hash (idempotency) and the content hash (selection binding). Replay returns the stored result before any price check.
3. RECONFIRM. KEEP re-asserts the stored price against the CURRENT need. UPDATE takes p_price_rsd. Both go through the helper, and a new version is written.
4. SELECTION. There is no price parameter. The requester pins need revision, response version and content hash. The server re-asserts the helper against the current need and copies agreement_versions.terms.price_rsd from the stored version (v_ver.price_rsd). agreements has no price column. The accepted amount is terms.price_rsd of the current agreement version. Connection platform cost is the literal 0 (REQUESTER_SELECTION_V1, PROMOTIONAL_FREE) and is a separate concept.
5. AFTER SELECTION. The only path that moves the accepted amount is the bilateral change flow (rpc_propose_agreement_change_v2 and rpc_respond_agreement_change). It accepts any whole number 1..2147483647, with no tie to task mode, basis or price. The other party consents, and the accept call carries no amount. That flow is the existing canonical contract (LIVE 9.3), not an accident.
6. WHO CAN WRITE. Only the RPCs write price (SELECT-only RLS policies on the response and agreement tables; the response tables grant no write to anon or authenticated). There are no price triggers or CHECKs beyond price>0. Price integrity is RPC-only. [SS-F07, SA-SEL-01, SA-SEL-06, SA-SEL-10, SM-P05..P07, LD-F05, LD-F06, PC-add]

SEMANTIC CORRECTION (SA-SEL-04 corrected): the server does NOT guarantee that a stored price is the total for the covered slots. That holds only for PER_PERSON and TOTAL. NULL basis and OFFERS are free of that tie. 'ukupno' is a UI label.

## 2. What the server treats as authority after PKG-049
Principle (CANONICAL_RULE, owner decision 2026-10-01 plus LIVE 9.2 'the plan invents no new price policy'): the requester-declared task price is the only price input. The server validates or derives every downstream amount from it and never from an unvalidated client value. For the application -> selection -> Agreement v1 chain this is ALREADY the live behaviour (see todayDetermines). PKG-049 as 'make the server enforce the requester price' is a no-op for MY_PRICE.

Concrete rule per mode and basis, using only what the canon defines (owner decisions 2026-09-19 plus the PKG-025A and PKG-033 rules):
- MY_PRICE, NULL basis: the server validates price = needs.requester_price_rsd whatever covered_slots is (legacy meaning, not reinterpreted, nothing backfilled). Undefined for NEW tasks with required_slots>1 (D1). Recommended default: unchanged.
- MY_PRICE, PER_PERSON: price must equal requester_price_rsd::bigint x covered_slots (6 people at 3000 gives 3000 / 9000 / 18000).
- MY_PRICE, TOTAL: covered_slots must equal required_slots and price must equal requester_price_rsd (one Agreement, no split, no rounding).
- MY_PRICE with no usable task price: FIXED_PRICE_NOT_READY, and the UI shows 'Cena nije navedena'.
- OFFERS: the worker's price IS the offer. The server cannot derive it. Its authority is the stored version row bound by content_hash (selection copies it, never takes a client price). The only rule is >0 / int4. No bound is defined (D4).
- Selection and Agreement v1: amount = stored version price, re-asserted against the current need. No client price exists at selection.
- Agreement amendment: currently free bilateral consent (existing contract, LIVE 9.3). Whether a MY_PRICE Agreement may deviate is UNDEFINED (D3).

Recommended default for what PKG-049 should be: do NOT apply any server body change on the current premise. Correct the registry, LIVE and receipt text. Add a fresh disposable plus HTTP-level proof as characterization evidence (no DEV change). Draft a function-only candidate only for the residual items the owner explicitly selects (D2, D3, D4, D1). Everything stays function-only so the closure certificate is untouched.
