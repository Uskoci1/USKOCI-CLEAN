## The static finding (read-only DEV bodies of 2026-10-02, md5 equal to the repository sources)

TASK path: `rpc_cancel_media_upload` on a READY photo takes the asset row FOR UPDATE and then, through `rpc_remove_task_photo`, the conversation row FOR UPDATE; `rpc_remove_task_photo` and `rpc_complete_media_upload_service` (a retry on a READY asset) take the conversation row first and the asset row second. A cancel that holds the asset and a remove/complete that holds the conversation wait for each other: a two-process cycle. The cancel of a not-ready upload takes no conversation lock, so the inversion needs READY. Agreement photo/voice paths take the per-account advisory lock before any row in every operation (CANCEL, SETTLE, CLAIM, send), so no inversion is expected there. Account closure (`rpc_prepare_account_closure`, exclusive closure key) holds nothing while it waits for the shared holders. No expiry or cleanup writer of the three media tables exists on DEV (14 writer functions, the closure redaction is dynamic SQL, cron has two jobs).

## What the proof will show (pre-registered, from the bodies)

`RC02-F1` / `RC02-F2`: the four task-path interleavings (cancel(READY) vs remove, vs completion retry, each with each victim) end in a 40P01 for exactly one session whose DETAIL is a two-process cycle; the other call succeeds; the final state is the single registered one. Every other interleaving serializes with no error except the registered refusals (`MEDIA_NOT_EDITABLE`, `MEDIA_COMMAND_CANCELLED`, `ACCOUNT_CLOSING`). A negative control (a scratch copy of the Agreement upload service with the row lock before the advisory lock) must deadlock; a positive control (the cancel copy with the conversation row first) must not. Nine deterministic conflicts must answer HTTP 409 / PT409. A green run means every outcome equals the registration, INCLUDING the registered deadlock (a finding, not a fix).
