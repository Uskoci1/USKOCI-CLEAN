# PKG-026 — remove the internal reservation admission blocker

Status: candidate prepared; not applied. Disposable CI proof pending.

The owner diagnosed a stopped AI conversation on the phone, then explicitly requested removing the reservation blocker so work can continue. This supersedes the temporary USD 5 admission cap as product intent. It does not authorize fabricating zero provider usage, deleting accounting history, changing keys, or sending test provider requests. The standing separate per-candidate DEV migration approval remains the final gate after a concrete candidate and proof.

## Observed failure

Canonical DEV had USD 4.777326 accounted against a USD 5 ceiling; USD 0.222674 remained but every LLM operation requires USD 0.25 admission. USD 4.35 belongs to 18 unsettled reservations. Unknown usage is not zero usage. Raising or resetting a counter would obscure the cause or recreate it later.

## Small compatible remedy

`supabase/candidates/pkg026_ai_test_cap_optional.sql` adds a private global boolean `reservation_cap_enforced`, default true, and explicitly switches it off in this owner-requested application. The legacy USD 5 value remains for historical/configuration compatibility, but it is not enforced while the flag is false. The counter remains nonnegative and can grow above that old cap. It continues to represent a mixture of settled costs and unsettled conservative allocations, not a provider invoice.

Only the reserve RPC's budget comparison is conditional. Existing APKs and deployed Edge functions keep using the same RPC signature and response shape. No APK installation or Edge deployment is needed. Reservations remain mandatory for operation identity, replay exclusion and existing metering. New requests can continue past the former cap, so the operator accepts provider charges without this internal USD 5 stop.

The service-only report explicitly returns `reservationCapEnforced:false`, a null cap, null remaining call allowance and `capIsACallCounter:false`. It keeps unknown total spend unknown. No settlement algorithm, prior reservation, user content, admitted account, token limit, voice duration limit, model or key changes.

Authentication, the existing admitted-account list, account closure restriction/lock, enable switch, price validity, operation uniqueness, replay denial and cross-account conflicts remain. Per-call input/output limits are unchanged. The setting is operational metadata on an existing singleton, not personal data; no new retention dataset or erasure operation is required.
