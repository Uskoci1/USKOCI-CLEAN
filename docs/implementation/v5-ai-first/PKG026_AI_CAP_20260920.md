The legacy USD 5 value remains for historical/configuration compatibility, but it is not enforced while the flag is false. The counter remains nonnegative and can grow above that old cap. It continues to represent a mixture of settled costs and unsettled conservative allocations, not a provider invoice.

Only the reserve RPC's budget comparison is conditional. Existing APKs and deployed Edge functions keep using the same RPC signature and response shape. No APK installation or Edge deployment is needed. Reservations remain mandatory for operation identity, replay exclusion and existing metering. New requests can continue past the former cap, so the operator accepts provider charges without this internal USD 5 stop.

The service-only report explicitly returns `reservationCapEnforced:false`, a null cap, null remaining call allowance and `capIsACallCounter:false`. It keeps unknown total spend unknown. No settlement algorithm, prior reservation, user content, admitted account, token limit, voice duration limit, model or key changes.

Authentication, the existing admitted-account list, account closure restriction/lock, enable switch, price validity, operation uniqueness, replay denial and cross-account conflicts remain. Per-call input/output limits are unchanged. The setting is operational metadata on an existing singleton, not personal data; no new retention dataset or erasure operation is required.
