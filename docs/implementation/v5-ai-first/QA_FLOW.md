# Contextual Task questions

133 connects existing RU-4B Q&A to the canonical public and requester Task details through the hidden `/pitanja-zadatka?needId=…` route. Server context determines the role. There is no new global tab or chat. The existing public reader still returns only answered questions for the current public revision; it additionally excludes blocked and closure-restricted account pairs. Requester pending questions appear first; historical revisions remain clearly separate.

The device persists only account/Task coordinates, command UUID, operation, revision and SHA-256 of the exact trimmed submitted text. It stores no proposed text. Mount, resume and manual refresh read the original actor-owned command receipt. An absent receipt never authorizes automatic resubmission or a new UUID. Explicit replay requires the same text and UUID. An interrupted or unfocused client cannot submit after its awaited local persistence completes. Closing the route does not cancel a server transaction already dispatched. Exact receipt validation precedes clearing the journal.

134 implements the owner-approved AF-D11 numeric policy: 500 Unicode characters per question, 1000 per answer, at most 10 accepted questions per account in a rolling 24 hours, at most 3 per account and Task in that interval, and a 60-second account ASK cooldown. Duplicate questions are compared across the same Task and revision after lowercasing, trimming and collapsing whitespace. Ignored/reported accepted questions still count. Idempotent replay returns before quota checks and never adds a second count.

The existing accepted question ledger is the quota source. Final canonical ASK serializes by account and Task/revision, rechecks after acquiring both transaction locks, and timestamps an accepted question after those locks. Service preflight reserves no quota: the canonical write repeats all checks. Existing contact-floor, block/closure, exact policy and answer materiality gates remain in place. Numeric readiness grants no semantic ALLOW. A material answer must use the existing Task edit/review/publication path.

135 connects question and answer submission to the durable classifier service. Recovery reads the original canonical command first, then the classifier state. PROCESSING is never resubmitted automatically; READY can replay the same exact text and UUID without another provider call. Explicit cancellation preserves provider/budget evidence and clears local intent only after authoritative CANCELLED or a matching COMMITTED receipt. A committed answer wins a cancellation race. A material answer returns the requester to the existing Task edit flow. Provider configuration and paid test activation remain separate from this source integration.
