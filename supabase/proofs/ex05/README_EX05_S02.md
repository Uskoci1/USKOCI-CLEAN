# EX-05 S02 / RC-02: media-cancel lock order, a targeted CONCURRENT proof on a disposable chain

**Evidence level: SOURCE + offline unit tests (`node --test supabase/proofs/ex05/*.test.mjs`) + read-only DEV SELECTs of 2026-10-02 (function bodies, md5 pins, trigger definitions, cron, catalog). The chain proof itself has NOT run yet: its first CI run is its first evidence. A disposable chain is NOT DEV, nothing here is device or native proof, nothing was applied to DEV or a provider, and no production function body is changed or proposed.** Registry/plan status is the root's to record (this slice writes no `docs/control` file).

## What is claimed and what the live bodies say

RC-02 (`docs/implementation/audit-20260924/RELEASE_CONTRACTS.md`, REPORT.md line 50, EX05 scope gap G11, plan 10.2): the cancellation of an upload locks the asset row before the conversation row, the opposite of the other media writers, so concurrent callers can form a wait cycle. The audit proved this from SOURCE and said "not an observed runtime deadlock". Read from canonical DEV on 2026-10-02 (the md5 of every body is pinned in `ex05_s02_pins.json` and equals the repository source, see the offline ties), the lock orders are:

| operation (role) | order of acquisition |
| --- | --- |
| task `rpc_cancel_media_upload` on a READY photo (authenticated) | closure key shared -> advisory `media-upload(account,key)` -> **asset row FOR UPDATE** -> `rpc_remove_task_photo`: closure key (re-entrant) -> **conversation row FOR UPDATE** -> asset row (held) -> advisory `media-evidence(account)` (trigger) -> facts rows |
| task `rpc_remove_task_photo` (authenticated) | closure key shared -> **conversation row FOR UPDATE** -> **asset row FOR UPDATE** -> advisory `media-evidence` -> facts |
| task `rpc_complete_media_upload_service`, retried on a READY asset (service) | closure key shared -> plain asset read -> **conversation row FOR UPDATE** -> **asset row FOR UPDATE** (returns the READY asset) |
| task `rpc_cancel_media_upload` on a not-ready upload | closure -> advisory -> asset row; **no conversation lock** (it only deselects) |
| Agreement photo/voice upload service `CANCEL`/`READ`/`FAIL` (service) | plain agreement read -> **advisory `photo|voice(account)`** -> upload row FOR UPDATE -> advisory `media-evidence` (UPDATE trigger) |
| Agreement upload service `CLAIM`/`STAGE`/`DISPATCH` | closure keys (both parties) -> advisory `photo|voice(account)` -> agreement row FOR SHARE -> safety pair (shared) -> upload row FOR UPDATE -> evidence advisory |
| Agreement upload service `SETTLE` | advisory `photo|voice(account)` -> upload row FOR UPDATE -> evidence advisory |
| Agreement send (authenticated) | closure keys (both) -> **advisory `photo|voice(account)`** -> advisory message(account,cmid) -> agreement row FOR SHARE -> safety pair -> (BEFORE INSERT guard) upload row FOR UPDATE -> evidence advisory |
| account closure `rpc_prepare_account_closure` | **closure key EXCLUSIVE** first (waits for every shared holder), nothing held while it waits |

So the inversion exists in the TASK path only (cancel of a READY photo against remove or a completion retry, which both take the conversation row first). The Agreement paths take the per-account advisory lock before any row everywhere, so they should serialize without a cycle. These are the **pre-registrations** (written from the bodies, never from a run); the proof can contradict them.

## What the proof does (`ex05_s02_proof.mjs`, driven by `.github/workflows/ex05-s02-rc02-proof.yml`)

* **Genuinely concurrent sessions.** One `psql` process per transaction, all held open at the same time, with `application_name` per session, `set local role authenticated|service_role` plus the JWT claims of a real signed-in account (real session id), `set local statement_timeout`, and `set local deadlock_timeout` (the proof role must be allowed to, else the run is red with `DEADLOCK_TIMEOUT_NOT_SETTABLE`) to steer which session of a cycle is the victim.
* **Gate + queue discipline.** A *gate* session (the login role) holds exactly one lock a real caller needs (the conversation row, the asset row, the upload row, the agreement row, a per-command or per-account advisory lock, or the closure key). The first caller is started and OBSERVED blocked behind the gate in `pg_stat_activity`/`pg_blocking_pids` before the second caller starts; the second is observed blocked behind the first (or the gate); only then the gate is released. Queue order of PostgreSQL row locks is FIFO (heavyweight tuple lock), so "first behind the gate" decides who takes the conversation row first. A row gate prints how many rows it locked and the engine refuses zero. No step is a sleep race.
* **Outcome classes.** `DEADLOCK` (exactly one victim with SQLSTATE 40P01 whose DETAIL names a two-process cycle, a surviving partner, the registered victim), `SERIALIZED` (no error except the registered business refusals, one registered final state), anything else is red. A `40001` in any session is always red. Every scenario reads the final row state afterwards (asset state/selected/dispatch/in-draft, tombstone count, message count, closure request).
* **PT409 contract (HTTP).** Nine deterministic conflicts (task complete of an unsettled upload, stale attempt, cancel through another conversation; per Agreement kind: same key with other input, stale version, same message id with another asset) must answer HTTP 409 / SQLSTATE `PT409` over the real PostgREST with the registered message.

## The interleavings (35, data in `ex05_s02_catalog.mjs`)

TASK path (17): `T1A/T1B` cancel(READY) vs remove, remove queued first, each victim (REGISTERED DEADLOCK, finding RC02-F1); `T2A/T2B` cancel(READY) vs completion retry (REGISTERED DEADLOCK, RC02-F2); `T3` remove behind cancel, `T4` completion retry behind cancel, `T5` second cancel of a READY photo (waits on the per-command advisory lock), `T6` two cancels of an absent command (one tombstone), `T7A/T7B` claim vs cancel of an absent command (the delayed claim is refused `MEDIA_COMMAND_CANCELLED`, 55000), `T8A/T8B` settlement vs cancel of a DISPATCHING upload (no lost update of `selected`), `T9` the cancel of a not-ready upload answers while a completion is parked on the conversation row (the inversion needs READY), `PC1` positive control, `CL1` closure prepare waits for a parked cancel, `CL2A/CL2B` a cancel waits at the closure key and then proceeds / is refused `ACCOUNT_CLOSING` (42501).
Agreement path, once for photo and once for voice (9 each): `A1` send first then cancel, `A2` cancel first then send (refused `MEDIA_NOT_EDITABLE`, 42501), `A3A/A3B` settle vs cancel of a DISPATCHING upload, `A4` second cancel, `A5A/A5B` claim vs cancel of an absent command, `NC_A` negative control, `CL3` closure prepare waits for a parked send.

**Registered outcome of each** is in the catalog (`expect`), with its single documented final state. For the deadlocks the registered final state of the asset depends on the victim: the cancel survives -> the photo leaves the draft; the completion retry survives -> the photo stays in the draft and the cancel received 40P01 (an error, not a lost update: the aborted call changed nothing).

## Controls (so the proof can fail)

* **Negative control `NC_A_INVERTED_CANCEL_VS_SEND_{PHOTO,VOICE}`.** A scratch copy (schema `ex05_scratch`, built at run time from the chain's own `pg_get_functiondef` by swapping exactly two statements, exactly-once anchors, md5 of the stored body compared with the intended body) of the upload service takes the upload row BEFORE the per-account advisory lock. The A1 interleaving must deadlock. If the harness cannot see a wrong order (sessions not truly concurrent, queue order wrong) this control comes back SERIALIZED and the run is red (`CONTROLS`).
* **Positive control `PC1_ORDERED_COPY_OF_CANCEL_VS_REMOVE_NO_DEADLOCK`.** A scratch copy of `rpc_cancel_media_upload` with one added `for update` on its first conversation read (the conversation row first, the order of its siblings). The T1 interleaving must NOT deadlock. It shows the lock order is the cause. It is a **diagnostic control, not a candidate**: no file under `supabase/candidates` is written and nothing is proposed for application; a fix is its own gated slice (`primeni`, certificate check).
* **Mutation kill.** Both controls are also judged by the registration of their REAL sibling (the scratch copy renamed to the real function's session: `A1_SEND_FIRST_THEN_CANCEL_<KIND>` for the negative control, `T1A_...` for the positive one) and must be RED there with a `CLASS_MISMATCH`: the injected change, and nothing else, is what flipped the outcome the real function is registered to have (`redUnderTheRealSiblingRegistration`, required by the admission).
* **Mutation tests of the verdict** (offline): every way the verdict, the findings, the controls and the admission can be satisfied wrongly is refused by `ex05_s02_catalog.test.mjs`.

## Chain fidelity (the label on every result)

The chain is the unchanged DEV closure surface before D12 minus EX-04: source147 -> PKG-050 (stages 03-18, which include PKG-046a, the cancel function and the Agreement photo functions), A1/B3a/B3b (19-21), P0/P4/P5/B3c (22-25), B24 part 2 in relaxed pre-image mode (26, the Agreement photo functions equal DEV after it), the exact Voice B1 DEV application (27, the voice functions). **It is NOT DEV**: it lacks pkg051a, PKG-045b P0, P6 rollout v3, EX-04, D12 and B24 part 1; its ledger, OIDs and certificate are chain-internal. B24 part 1 is not on the chain, so the seven functions it converts (the six task media functions and `rpc_prepare_account_closure`) carry their pre-B24 body there; the proof converts them with the very transformation of the candidate (`replace(pg_get_functiondef, '40001', 'PT409')`) and requires the converted md5 to equal the DEV md5 and the certificate digest to be unchanged. The pin gate compares 42 function bodies (31 of them core for the lock order) and 11 trigger definitions with the DEV md5, plus the writer census (the 14 functions that write the three media tables; no expiry or cleanup writer exists on DEV; the closure redaction is dynamic SQL and is not interleaved). A core difference makes the run red (`CHAIN_NOT_DEV_FAITHFUL`), a context difference is a warning. Dispatch with `pin_gate_only` for a cheap first cycle that prints every difference.

## Reading a run

* **Green** means: every interleaving ended as registered, the controls were detected, PT409 held, the chain was DEV-faithful. It **includes** the registered task-path deadlock: findings RC02-F1/RC02-F2 `REPRODUCED` are findings, not fixes (the step summary and a `::warning` annotation say so first).
* **Red lines to read first:** `CHAIN_NOT_DEV_FAITHFUL` (conclusions are about the chain only), `CLASS_MISMATCH` / `UNEXPECTED_DEADLOCK` (a deadlock where serialization was registered is a NEW finding: the report holds its exact statements, DETAIL and CONTEXT; do not patch in this slice), `RC02-F1 NOT_REPRODUCED` (the static analysis is refuted for that path on this chain: read the observed class and the edges before concluding), `WAITS_NOT_OBSERVED`/`STEP_TIMEOUT` (the sessions were not concurrent the way the scenario needs: a proof defect, not a verdict), `SQLSTATE_40001_OBSERVED`, `STATEMENT_TIMEOUT`.
* The artifact `ex05-s02-rc02-<sha>-<run>` holds `ex05-s02-report.json` (per interleaving: statements, observed edges, snapshot, cycle, victim, 40P01 DETAIL/CONTEXT, outcomes, final state), `ex05-s02-report.md`, the unit-test output, the checker output, the stage list and the console tail.
* `workflow_dispatch` inputs: `pin_gate_only` (stop after the pin gate), `only` (comma list of interleaving ids; unknown ids fail).
* **A partial run never reads as the proof.** With `pin_gate_only` or `only` the report carries `scope` (`PIN_GATE_ONLY` / `FILTERED`, else `FULL`), `resultLabel` is `PASS_PARTIAL` / `FAIL_PARTIAL` (never a plain `PASS`), the markdown and the step summary start with a bold `PARTIAL RUN (...)` line, and the final console line repeats it. A filtered report is admitted for the named interleavings only (controls and findings are then not required).
* **A killed or interrupted run still says so.** `ex05-s02-report.json` is written at start with `result: RUNNING` (no `finishedAt`): a report that stays `RUNNING` means the step was killed while a database call blocked. SIGINT and SIGTERM (a cancel or the step timeout) write `FAIL` with a `TERMINATED_BY_<signal>` line, kill every open session and still write the markdown (a synchronous psql call can delay the handler by its own 20 s timeout).
