## How a text becomes a kind (the whole rule)
* Each value of the input array is folded on its own: `btrim`, lower case, the Serbian Latin letters c-caron, c-acute, s-caron, d-stroke, z-caron (both cases) and the whole Serbian Cyrillic alphabet (27 letters per case, plus the three digraph letters `Lj`, `Nj`, `Dz` handled first) become plain lower-case Latin letters. One Latin stem therefore serves the Latin text, the diacritic-free text and the Cyrillic text.
* A kind is named when ONE of its stems occurs INSIDE one folded value (substring, exactly as the old regular expression alternatives did). A stem is never assembled across two values. Stems are lower-case ASCII letters and inner spaces, at least four characters (a shorter or unfoldable stem can never match; the postflight reports it as `STEM_NOT_FOLDED`).
* Text that names no kind returns nothing, so an unknown word is never a kind and two DIFFERENT unknown words never match each other (the matcher then falls back to exact text containment, unchanged). NULL and empty arrays answer `{}` before the registry is read.
* The registry is validated on every call: the head row (`WORK_KINDS_HEAD_V1`, the eleven names in order, the fold version) and exactly the eleven kind rows (`WORK_KIND_V1`, `kind` equal to the key, `stems` an array). Anything else raises `WORK_KINDS_REGISTRY_INVALID` (SQLSTATE 55000, never 40001): a damaged registry stops matching loudly instead of silently matching nothing. The classification version `WK-1` is data: the function validates the head row but does not read the version string (a version bump is a data edit; carrying it into delivery payloads is NOT part of this candidate, see "Open items").

## Why this is certificate-neutral (read on canonical DEV with SELECTs, 2026-10-02; asserted again by the application itself)
* `private.work_kinds_v5(text[])` is NOT one of the 88 signatures of `private.closure_source_digest_v5()`, is not named in the program digest, the schema digest or any function they concatenate, and is not a trigger function (`pg_trigger.tgfoid`); its only dependents are two functions (`private.match_detail_without_calendar`, `private.dispatch_cheap_candidate_admitted`), no view, rule, index or default depends on it (read from the catalog).
* No table, column, constraint, trigger, policy, ACL, owner or publication changes. `private.marketplace_config` keeps its exact three-column, triggerless, ruleless shape (the primary key is pinned by the md5 of its definition). A data row is not part of any digest (PKG-051a added its rows with the digest unchanged).
* The application asserts `private.retention_ai_source_ready()` true and `closure_source_digest_v5()` equal to the certified value BEFORE and AFTER, inside the same atomic statement; the proof asserts the closure, the schema digest and the program digest equal before/after, and the postflight reports a `CERTIFICATE` problem otherwise. ## Transports: how the guarded text is produced and sent (nothing is sent by the author)
A connector deploy resolves unicode-escape text and wraps what it sends, so the application text carries a hash guard. Two transports exist and they differ:
* **PLAIN** (`execute_sql` / psql `-c`): `python supabase/proofs/ex06/build_ex06b.py --wrap supabase/candidates/ex06b_alias_registry.sql --wrap-out <path>` (committed copy `s06/guarded/ex06b_alias_registry.plain_guard.sql`). The D12 / Voice B1 method: absolute-position sha256 of the span of `current_query()`, then nothing but line feeds and `--` comment lines (the trailer `execute_sql` appends is accepted).
* **APPLY_MIGRATION** (the connector's `apply_migration` wraps the text and holds it TWICE in `current_query()`; the absolute-position guard is REFUSED there, as the first D12 attempt showed): `python supabase/proofs/ex06/build_ex06b.py --wrap-migration supabase/candidates/ex06b_alias_registry.sql --wrap-out <path>` (committed copy `s06/guarded/ex06b_alias_registry.apply_migration_guard.sql`). The marker-based method of `supabase/proofs/d12/wrap_apply_migration.py`, adapted to the marker `-- EX-06 ex06b alias registry: DEV application text.`: exactly two occurrences, both hashed, followed by the connector's own history statement. The same two forms exist for the revert (marker `-- EX-06 ex06b alias registry revert: DEV revert text.`).
The guard hashes the file WITHOUT its trailing line feed (span 22,257 characters, sha256 `6600d2b8b7df574e8b3559d407c49d38bc81beeef3d2c8076e814fac2627b780`; revert span 17,193 characters, sha256 `8d4964cb865090cacddc3a675069e67e47824256fdd380d496162dcc4e354c84`). `--selftest` runs both guards against models of what each connector sends (measured read-only on DEV for D12): accepted are the exact text with and without its final line feed (plain: also with the connector's trailer comments); refused are one changed byte, a statement after the candidate, anything before the guard (plain) and a changed byte inside the history copy (apply_migration). A truncation or a missing or third copy is not self-tested (the apply_migration predicate requires exactly two occurrences, the plain guard hashes the whole span). A refusal raises `EX06B_APPLY_TEXT_INTEGRITY` (SQLSTATE 55000) before anything else runs. Whether the real connector accepts the guard is proved only by the application itself (nothing applied is the failure mode).

## Editing the registry later (data, not a migration)
An alias is ONE row edit of `private.marketplace_config` (the `stems` array of `work_kind:<KIND>`), under the owner's word, without a migration, a certificate change or an APK. Rules: lower-case ASCII letters and inner spaces only (what the fold can produce), at least four characters, no new `work_kind:*` key for a new kind (it is ignored), never a stem that is a common word of another trade. The postflight then shows the row as `REGISTRY_ROW_DIFFERS`: record the edit in the ledger receipt of that edit. The proof exercises the data edits on the disposable chain only (rolled back).
