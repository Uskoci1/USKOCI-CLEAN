# EX-06 S03 - corpus-driven matching contract proof (harness)

Run: `.github/workflows/ex06-s03-matching-proof.yml` (disposable chain source147 -> PKG-050, actual Auth and PostgREST). Offline, no database and no dependency: `node --test supabase/proofs/ex06/lib/*.test.mjs` (127 tests).
**Evidence honesty.** Nothing in this directory has been run against a database or in CI yet. The offline tests run the real fixtures, runner and adapter against fakes and against a *simulated* backend (`lib/sim_backend.mjs`, its matcher oracle written for the test; `lib/proof_main.test.mjs` runs the whole orchestration and the second section against it): they show that the harness runs end to end and that its guards fire, not what the chain does. Files: entries `ex06_s03_proof.mjs` (-> `lib/proof_main.mjs`) and `ex06_s03_extension_report.mjs` (-> `lib/extension_report.mjs`); `lib/{pins,corpus,s02_adapter,compare,runner,fixtures,geo,timeutil}.mjs`; tests and the simulation `lib/*.test.mjs`, `lib/test_support.mjs`, `lib/sim_backend.mjs`. Review rounds: `S03_REVIEW_DISPOSITION_R1.md` (round 1, 41 findings), `S03_REVIEW_DISPOSITION_R2.md` (round 2, 23 findings; this state).

## 2. What the proof does (`ex06_s03_proof.mjs` -> `lib/proof_main.mjs` `runProof`)
1. Harness self-tests (every gate class of the comparator reports a mismatch); pg_cron jobs `uskoci%` paused (a background tick must not run a wave before the harness does).
2. **Pin gate**: 11 of the 12 S01 function-body pins that stage 18 reaches (`lib/pins.mjs`; the 12th, `public.rpc_begin_push_send` fc76b344, is read after the extension by `ex06_s03_extension_report.mjs`). A difference is reported and downgrades the label; it never fails the run. Label: `MATCH/DISPATCH/EVENT FUNCTION BODIES == DEV (... ; helper functions, config rows and triggers not pinned)`; the second section says `11 pins equal at the proof point (chain without the extension) + the 12th equal after the extension (different chain state)`, never a bare "12 pins". A difference with no machine-checked explanation prints what the pin records about itself (`pin.evidence`) in the table. For information only (not pinned, not in the label): md5 of 10 dependency functions (`schedule_fit`, `worker_dispatch_time_admitted`, `worker_available_periods`, `availability_is_future`, `worker_calendar_conflict`, `lower_arr`, `haversine_km`, `effective_radius_km`, `identity_admitted`, `candidate_budget`), sha256 and wave sizes of the `marketplace_config` rows `dispatch_normal`, `dispatch_urgent`, `urgent_activation_policy`, and a catalog fingerprint (md5 of every function body and trigger of public and private; unchanged by the run, asserted).
3. **Certificate**: certified, live, erasure source and binding must be equal and ready at the start, unchanged at the end (harness error otherwise). The chain digest is compared with DEV's 58447d77 for information only (the chain stops before B24 part 2, voice B1 and pkg045b-p0).
4. **Canary** (first, mandatory, product path, seven cases): fit + unfit (tool); a scheduled FIXED_WINDOW task (covering availability, vehicle); a worker in another city (radius); **REMOTE**, **POINT_TO_POINT** and **MULTI_STOP** geographies (the shapes the S02 corpus uses besides STATIONARY: a defect in a location value, a waypoint pin or the end slot is a canary failure, not a quiet refused corpus case); the **world gate** (a REAL requester's task reaches a REAL worker and not a TEST-world worker, which `match_detail` still calls eligible: private.dispatch_cheap_candidate_admitted holds `accounts_same_world`, named by `notDeliveredBecause`); and the DRAFT control in every case. Any disagreement is a `HARNESS_ERROR` (exit 1), never a finding.
5. **Per corpus case**: requester and workers through real Auth (a bounded retry on HTTP 429, section 5) and the product's writers; foreign ACTIVE workers parked (restored at the end); the task through the **product path** (conversation -> synthetic proposals -> review with the city table's pins -> accept -> evaluate (synthetic ALLOW, no provider) -> publish); **read back** of the task (status, lists, price, window, coordinates, `urgent`) and of every worker (lists, location, capacity, the CONTENT of the stored availability rules and windows, bypass columns, world) (`FIXTURE_NOT_APPLIED:<field>` otherwise); `private.match_detail(nid, pid)` per worker (the function the wave calls), shape-validated; the stored coordinates must give the matcher's `distanceToStartKm` (haversine within 0.02 km); ONE `private.dispatch_next_wave`, shape-validated (SENT, or STOPPED without `reason`; round 1 / policyWaveNo 1; the `dispatch_rounds` row must agree); deliveries and OPPORTUNITY_AVAILABLE events; comparison with the corpus; hidden kinds of the **stored** row (exactly one row holding a JSON array: an empty read is a harness error, so the seven `unclassified` cases cannot pass vacuously); retire everything created (half-built workers and orphan tasks included).
6. Reports `ex06-s03-report.json` / `.md`, the `RESULT` line and workflow annotations. When a call timed out or was aborted, the active backends of the disposable database are recorded first (which query hung) and the stuck ones terminated, before the fixtures are retired.

## 3. Result, exit code, environment
`PASS | FINDINGS | SMOKE_ONLY | PARTIAL | HARNESS_BROKEN`. SMOKE never yields PASS; a capped run, a buildable case that did not run, a DEGRADED case (a direct insert), a case the product path **REFUSED** (never compared) or a **SHAPE_DEGRADED** case (the schedule shape the corpus asked for could not be built) yields PARTIAL; a harness error is HARNESS_BROKEN (exit 1); findings exit 0 (2 with `EX06_STRICT_FINDINGS=1`). A result is never quoted without its scope: `PASS on N of M cases, K refused, L skipped, X of Y leaves compared` (the RESULT line, the first lines of the markdown, a `::notice` for PASS and FINDINGS); `report.scope` and `corpus.compared / refused / errored / leavesComparedAtRun` are computed from the case entries at run time. A green job is not evidence: read the RESULT line (`corpus=`, `cases ran/total (compared, refused, errored)`, `skipped`, `positive-only`, `SHAPE_DEGRADED`, asserted counts, `tasks: product/direct`, `unconsumed`, `findings`, `auth accounts / 429 retries`) or the `::warning` / `::error` annotations the proof prints (a refusal is reported on its own line and is never counted as a matcher disagreement).
`EX06_NEED_PATH` = `product` (workflow) | `direct` | `auto` (the last two are diagnostic: every such case is DEGRADED and listed with the facts the direct insert dropped; their assertions are counted apart, the run is PARTIAL, not vacuous). A product refusal of a READY case at review/accept/evaluate/publish **or of the proposals themselves (`provider_turns`: the service RPC validates the corpus's own facts)** is a FINDING `PRODUCT_PATH_REFUSED_READY_CASE`, never a fallback; a refusal at `open_conversation`, a turn that cannot be claimed (`EX06_TURN_NOT_CLAIMED`), a timeout or an abort is a harness error. `EX06_REQUIRE_CORPUS=1` (workflow): no corpus file is an error. `EX06_CORPUS` (explicit file), `EX06_MAX_CASES` (positive integer), `EX06_STRICT_FINDINGS`, `EX06_ARTIFACT_DIR`, `EX06_STAGES_FILE`, `EX06_CATALOG_FILE`.

## 4. The S02 corpus (`lib/s02_adapter.mjs`, a TOTAL adapter)
`supabase/proofs/ai/corpus/ex06_contract_corpus_v1.json` (EX06_CONTRACT_CORPUS v1) is converted into the normalised shape of `lib/corpus.mjs`. Every key of the root, a case, `expected`, `expected.review`, `expected.kind`, a reference-worker row, its `profile` and its `expect` is MAPPED or IGNORED **with a reason** (the tables are exported and tested); a new key throws `S02_KEY_UNKNOWN`. A key that is mapped on one family and would be dropped on the other (`referenceWorkers` on a WORKER case, `referenceTasks` / `referenceAssumes` on a TASK case) throws too. The ignored publication and review keys that carry assertions about the READY state are **tripwires**: a mapped READY case whose `publicationOutcome` is not ALLOW, whose `review.missingRequired` is not empty, or whose `canPublishFromAiAlone` / `humanConfirmationRequired` contradict READY throws `S02_READY_CASE_CONTRADICTS`. What S03 cannot exercise is reported **UNCONSUMED**, never dropped. The numbers of the offline run against the real file (a tripwire in `s02_adapter.test.mjs`; update both when S02 changes):

Consumed per built worker: `responseAllowed`, `dispatchEligible`, `hardBlockers` (exact set), `dispatchBlockers` (exact set); `eligibility` is validated against them AND against the blocker arrays at load (a corpus that contradicts itself throws `S02_ELIGIBILITY_INCONSISTENT`) and `unknownCapability` against the profile; `sourceReadingPrediction` (T-031) is carried as an annotation next to a finding. `kind.expected` (`unclassified` = nothing) is asserted against `private.work_kinds_v5(array_prepend(category, required_skills))` of the **stored** task (the input of the exclusion gate); the skills-only result (the service-match arm) is recorded next to it. The synthetic fact texts are built from the corpus' canonical items and `mustMention` words; the conversation `turns` are never used or copied. S02 has no delivery/event keys: they are checked as **derived invariants** (eligible => delivered; not eligible => not delivered; event iff delivery) and counted apart.
**Every case needs a negative of the CORPUS that names its cause** (the harness's own DRAFT control does not count): without one, and without the explicit `positiveOnly`, the case is a harness error `UNDISCRIMINATING_CASE`.
Findings the corpus itself predicts (author note A3: the corpus reads radius as city-name equality, the matcher uses geodesic distance when both positions exist; T-031 is a stem false positive) are expected S03 findings, not harness defects. Two things to read before judging a finding: a task of kind `TOMORROW_FLEXIBLE` / `WEEK_FLEXIBLE` that stores **no** `starts_at`/`ends_at` is refused for every worker by `worker_dispatch_time_admitted` (T-003 and T-006 would then show OUTSIDE_AVAILABILITY for the fit worker: a product finding, and SHAPE_DEGRADED says the harness could not build the schedule either), and calendar-busy workers are not built.

## 5. Fixture fidelity (`lib/fixtures.mjs`, `lib/geo.mjs`, `lib/timeutil.mjs`)
* **City table** (`geo.mjs`): Novi Sad, Petrovaradin, Futog, Beograd, Zrenjanin, Subotica, Sremska Mitrovica, Niš at two-decimal centres; used for the task pin (0.0025 degrees inside the cell, so round and floor agree) AND the worker position; an unknown city throws `EX06_CITY_UNKNOWN`. `anchorCity` is the city whose point the product stores as the coarse coordinates (AREA_BASED with a service area: the service area's), `primaryCity` the one of the city text (the start's first); they differ only for a geography that names two cities, which no S02 case does. Niš - Novi Sad is about 272 km (inside the 300 km candidate search of the wave); Niš - Subotica (> 300 km) is outside it, which does not matter because that worker is outside the radius anyway.
* **Availability shapes** (`timeutil.availabilityFor`): AVAILABLE_NOW_AND_SCHEDULED / SCHEDULED_ONLY / AVAILABLE_NOW_ONLY / NONE_DECLARED -> the document the writer accepts; a covering weekly rule in the Europe/Belgrade weekday and wall clock (an AVAILABLE window across midnight or near a DST change). `createWorker` returns `shapeCoverage {shape, wanted, got}`: a shape that wanted coverage and got `NONE` was NOT built as the corpus says (SHAPE_DEGRADED).
* **Rebase**: every absolute `need.starts_at`/`ends_at` is shifted by `delta = CI now - corpus.clock.nowUtc` (duration kept; the delta is in the report); a Belgrade offset is re-expressed with the zone's REAL offset at the new instant (a winter window moved into summer reads +02:00), any other offset is kept; a window that is not at least 30 minutes ahead is `CASE_TIME_NOT_FUTURE`.
* **Workers**: `skills: []` ACTIVE workers are *activated, then cleared* (`rpc_complete_worker_profile` refuses an empty list; the owner UPDATE afterwards is a product state); `years_experience`, `exclusions`, `minimum_fee`, preferences by a labelled bypass (gap G04: no writer); `world: 'TEST'` through `rpc_admit_account_lineage_service`, which reads the account's lineage first (`rpc_read_account_lineage_service`: the writer checks the revision before it recognises a restatement and raises 40001 for a stale one) and never admits an account that already is in a TEST lineage; a worker built on a given account takes that account's world; nested profile keys are validated exactly.
* **Auth capacity**: the proof signs in one account per requester and worker. In the simulation the whole real corpus creates **219 accounts** (7 canary cases + 37 corpus cases, a DRAFT control each); every other proof under `supabase/proofs` makes ten or fewer. The stack is a plain `supabase init`, so the CLI's default `[auth.rate_limit]` (per IP and 5 minutes) applies to the password sign-ins; that is NOT verified (the config of the real stack was not read). The workflow prints the limits into the job summary before the proof. `rt.actor` is wrapped in a bounded retry that recognises HTTP 429 / `over_request_rate_limit`: 30 s steps, 6 minutes per account and 20 minutes per run, each call also bounded by a timeout; a retry creates a new account; the report prints accounts created, retries, time waited and failures (`report.auth`). If the limit bites (a limit of 30 sign-ins per 5 minutes would need about 30 minutes of waiting, more than the 20 the run allows itself), the run ends HARNESS_BROKEN with the numbers, not silently; the next step is a stack config with a higher limit or a smaller case count (`max_cases`), decided from that first record. No account is reused across cases (an account's open conversation and profile state would leak between cases).
* **Controls**: every case also builds a DRAFT copy of the fit worker (`control-restricted`), counted apart; a case without an eligible-worker anchor or without a negative of the corpus that names its cause is a harness error in a contract corpus (explicit `positiveOnly` / `noEligibleWorker` opt-outs are listed).
* **The labelled direct insert** (`EX06_NEED_PATH=direct|auto`, facts the product cannot carry, `bookWorker`): `private.guard_need_write` refuses an INSERT that names `task_country_code` / `task_timezone` unless `uskoci.need_region = 'CONFIRMED_REVIEW'`, so BOTH tokens (`need_lifecycle`, `need_region`) are set as `pkg040_proof.mjs` does, and a non-remote task also gets its `public.need_geography` row. The simulation models the guard and refuses the statement without the region token; **the direct path and everything that uses it are UNPROVEN: no real database has run them.**
* **Counting**: corpus expectation fields (positive/negative, distinct gates), derived invariants, preconditions, controls, DEGRADED and UNREACHABLE_STATE are separate numbers.
