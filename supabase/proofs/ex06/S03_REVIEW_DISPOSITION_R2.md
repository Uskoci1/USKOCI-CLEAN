## Deferred sub-items (the core defect of each finding above is fixed)
* **D1 (R1F3, the "better" option)**: build the covering availability AFTER the publish from the stored `starts_at` / `ends_at` for TOMORROW_FLEXIBLE and WEEK_FLEXIBLE. Not done because it cannot help: the product stores no window for these kinds (reviewer 3 confirmed it from `worker_dispatch_time_admitted` and the publish path; the same holds for T-007 TODAY_FLEXIBLE, T-008 / T-027 REMOTE_ANYTIME and T-026 FLEXIBLE), so there is nothing to cover; and a rule built from a window the intent did not name would change what the corpus case says. If the product ever stores a window, the runner already notes it (`the product stored a window ... a covering rule could be built after the publish (not done)`). The required part (report SHAPE_DEGRADED, never a quiet available-now-only worker) is done.
* **D2 (R2F1 (3), R3F10, "cut the sign-ins")**: reusing a pool of accounts across cases, or minting sessions without a password grant. Not done: a reused account carries state between cases (an open AI conversation of a requester, profile status, availability and location revisions of a worker, a SUSPENDED retirement that no product writer undoes), and a session minted without the password grant would not be actual Auth; both would change what the proof tests without a database to check them against. The applied mitigation is the retry, the printed limits, the report of the accounts created and `max_cases`; whether the sign-in volume matters is the first thing the first CI run records (`auth-rate-limits.txt`, `report.auth`). If it does, the stack config (`[auth.rate_limit]`, which means a change to `ru5_device_ui_live79_env.sh` that no other workflow shares) is the straightforward next step.
