# B09 / PKG-049 characterization proof: disposition of the round-2 review (24 findings)

Source: three independent reviews of the round-2 proof (lenses FALSE-PASS / VACUITY, CHAIN FIDELITY AND WORKFLOW, SEMANTICS AND HTTP-LEVEL FIDELITY): 24 findings, 3 rated major (F0.0, F0.1 and F1.0, the last being the same defect as F0.1 seen by the second lens) and 21 minor, no blocker.
Round 3 applied every finding. Result: **24 FIXED, 0 DEFERRED**. Where a finding's proposed fix was changed on purpose, the "how" column says so (F0.8: the reviewers contradicted each other, see there). Ids are `F<lens>.<n>` in the order of the review file
(lens 0 = FALSE-PASS / VACUITY, lens 1 = CHAIN FIDELITY AND WORKFLOW, lens 2 = SEMANTICS AND HTTP-LEVEL FIDELITY). The files are `pkg049_pins.mjs`, `pkg049_lib.mjs`, `pkg049_proof.mjs`, the two test files, the workflow and the README.

**Evidence honesty.** Nothing here has run against a database. The unit tests ran offline in a scratch mirror of the integrator tip plus these files: `node --test supabase/proofs/pkg049/*.test.mjs` = 40 tests, all passing (they include the B24 derivation from the repository sources,
the P1b plan derived from the migration sources, the workflow-coverage checks against the real client module graph and the chain-defining files, and `pkg049_blocks.test.mjs`: dry runs of the proof's own P0 B24 stage loop,
P4(h) and P1b phase, cut out of `pkg049_proof.mjs` by markers and run against a stub `sql` and the REAL supabase-js client with a mock fetch, so a typo or a wrong request shape cannot hide until the first CI run; they prove the code, not the database). Every database and HTTP assertion added in round 3, including all 18 P1b attacks and the positive control,
is unobserved until the first CI run. The expected P1b outcomes are DERIVED from the grants, RLS and policies in the migrations (and tied to them by a unit test), not observed.

**Decisions taken before the round** (and where they landed): (1) new phase P1b, direct table writes. (2) the B24 stage tolerates only the four chain-drift guards, P4(h) keyed on the catalog, one transaction per function. (3) label honesty. (4) assertions that could not fail were made falsifiable.
(5) D1/D4/D6 labels everywhere a cell is asserted. (6) pins and tests: `rpc_read_task` pinned, both argument orders, CRLF-tolerant tests, a wider path filter.
